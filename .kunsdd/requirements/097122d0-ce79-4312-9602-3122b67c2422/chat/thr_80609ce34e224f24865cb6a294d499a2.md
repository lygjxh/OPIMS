## 推荐方案：Go + Vue 3 + SQLite → 单个 .exe

### 对你（使用方）意味着什么

你和同事拿到的是一个**单独的 .exe 文件**，双击运行，浏览器自动打开系统界面。不需要装 Python、Node、Java 之类的东西，跟打开一个绿色软件一样。

### 为什么这样选

| 你的需求 | 怎么满足 |
|---|---|
| **单机运行，双击即用** | Go 编译出来就是一个 .exe，所有东西（前端页面、数据库）都塞在里面 |
| **文件监控**（项目文件板块） | Go 的 fsnotify 是业界最成熟的文件变动监听库，新增/修改/删除文件秒级感知 |
| **以后要跑在鸿蒙上** | Go 可以交叉编译——在 Windows 上编译出鸿蒙能跑的程序，前端代码完全不用改 |
| **简洁美观的界面** | Vue 3 + Element Plus 组件库，表格、表单、仪表盘都是现成的专业组件，长得像企业级后台 |
| **中英双语切换** | Vue 的 vue-i18n 插件天然支持，做个切换按钮就行 |
| **数据备份恢复** | SQLite 数据库就是一个文件，备份就是复制这个文件，恢复就是替换回去 |
| **启动快、不吃内存** | Go 编译后的程序非常轻，比 Electron 方案小 10 倍以上 |

### 备选：.NET 8

如果你们找的开发者更熟悉 .NET（C#），这也是一个靠谱的选择，Windows 上原生兼容性好。但打包后体积会大一些（~100MB vs Go 的 ~20MB），启动也稍慢。两者都能满足需求，Go 更轻量，.NET 在国内开发者更多。

## Go vs Python — 对你的项目意味着什么

| 维度 | Go | Python | 谁更适合你 |
|---|---|---|---|
| **部署给非技术人员** | 编译成一个 .exe，双击运行。别人拿到手就是一个文件 | 想打包成 .exe 需要 PyInstaller，经常被杀毒软件误删，打包后体积大（100MB+），且容易缺依赖 | ✅ Go |
| **文件监控** | 标准库 + fsnotify，监听文件夹变动的首选语言 | 可以用 watchdog，但在 Windows 上问题多（权限、编码、性能） | ✅ Go |
| **启动速度** | 秒开，双击后浏览器马上弹出 | 打包成 .exe 后解压临时文件再启动，要等 3–10 秒 | ✅ Go |
| **内存占用** | ~20MB | 打包后通常 80–200MB | ✅ Go |
| **跨平台（Windows → 鸿蒙）** | 改个编译参数就能出鸿蒙版本 | 鸿蒙上跑 Python 非常折腾，基本等同于重写 | ✅ Go |
| **Excel 读写** | excelize 库，功能全面 | openpyxl / pandas，功能更强，但非核心优势 | 打平 |
| **Web 服务器** | 标准库自带，无需第三方框架即可跑 | FastAPI / Flask 需要装依赖 | ✅ Go |
| **开发者数量（国内）** | 较少，招聘成本高 | 非常多，容易找人 | ❌ Go |
| **开发速度** | 语法简洁但偏严格，写得稍慢 | 代码量少，原型出得快 | ✅ Python |

## 结论

**对你这个项目，Go 明显更合适**。一句话总结：

> Python 开发快但交付麻烦——你得让每个用户装 Python 环境或者塞一个臃肿的打包文件；Go 开发稍慢但交付极简——最终就是一个清爽的 .exe，别人不用知道它是什么语言写的。

唯一的短处是 Go 开发者比 Python 少，但这种单机 Web 系统的难度不高，任何一个合格的 Go 开发者都能胜任。如果开发者实在难找，选 .NET 当备选也比 Python 更适合你的交付场景。

我最建议优先完成的重构

如果只做三件事，我建议按下面的顺序：

## 需求 AI

这个建议方向是对的——它是 Go 社区的标准分层模式。但在我们当前项目语境下，我的看法是：**现在做收益不大，反而拖慢功能交付。**

### 为什么建议在理论上是正确的

```
Handler(HTTP) → Service(逻辑) → Repository(数据访问) → *sql.DB
```

这样做的好处：
- 每层可独立测试（mock Repository 就能测 Service）
- 换数据库只需改 Repository
- Handler 瘦到只做参数解析 + 调用 Service

### 为什么现在做不划算

| 当前现状 | 建议后 |
|---|---|
| 6 个 handler 文件，~900 行业务代码 | 增加 Repository 接口 + 实现 + Service 接口 + 依赖注入，至少多出 8-10 个文件 |
| SQLite 必须是单连接（`SetMaxOpenConns(1)`），注入 `*sql.DB` 没有任何实际切换价值 | 多了一层抽象但数据库永远不可能换成别的 |
| 单人开发、单机运行，没有团队协作和 CI/CD 需求 | 接口抽象的主要受益场景不存在 |
| 功能板块还有 5 个没做 | 重构期间功能开发停滞 |

### 真正的风险

这个项目的核心约束是 **SQLite + 单连接**。把 `*sql.DB` 注入进去看起来更"干净"，但实际上 SQLite 在 WAL 模式下并发读没问题，写操作本来就必须串行——全局单例和注入进去的同一个指针，行为完全一样。

### 什么时机值得做

- 项目接入第二个数据源（比如 Redis 缓存或外部 API）
- Handler 数量超过 20 个，单文件开始失控
- 需要给核心逻辑写单元测试，必须 mock DB

### 我的建议

优先完成功能板块（项目进度、质量、分包、人员），让系统能用起来。架构重构放到 v0.3 版本——那时候代码量上来了，重构的收益也看得见。现在的 `handlers → services → database` 三层虽然没严格依赖注入，但对于一个 6 文件、单人维护的项目来说已经足够清晰了。
